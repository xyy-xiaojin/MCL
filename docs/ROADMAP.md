# MCL 成熟度评估与路线图

> 结论先说：**核心链路（安装 → 启动 → 下载资源）已经能跑通，但它现在是一个"能用的 Demo"，
> 不是"能托付存档的启动器"。** 差距不在功能数量，而在三件事：
> 数据会不会被弄丢、出了问题能不能自己查、以及换台机器还能不能重建同样的环境。
>
> **0.03 更新**：P0-2/4/5、P1-6/7/10 已完成——磁盘预检、重复启动防护 + 结束游戏、
> 日志落盘 + 崩溃初判、Java 自动下载。版本隔离与 Fabric/Quilt 安装更早已完成。
> 剩下最要紧的：**Forge/NeoForge 安装**、**"修复文件"**、**启动失败分步诊断**。
>
> 这份文档里的每一条都是照代码核过的，不是按印象列的。对标对象：
> PCL2（VB.NET，Windows）、HMCL（Java）、Prism Launcher（C++/Qt）、Modrinth App（Tauri + Theseus）。

## 一、已经修掉的严重问题

这两条是写这份评估时顺手查出来的，都属于"界面说成功了、实际没生效"：

| 问题 | 原因 | 影响 |
|---|---|---|
| `.mrpack` 导入后游戏里什么都没有 | overrides 解压到 `instances/<slug>/`，而启动时 `--gameDir` 指向 `game/` | 整合包导入显示成功，实际一个 mod 都没加载 |
| 数据包装了看不见 | 落到 `game/datapacks`，Minecraft 没有这个全局目录 | 数据包永远不生效 |

修法：mrpack 现在直接解到 `game/`（已存在文件跳过），元信息单独记在 `instances/<slug>/instance.json`；
数据包改到 `saves/<最近修改的存档>/datapacks/`，一个存档都没有就明确报错而不是偷偷丢进死目录。

## 八、一个更根本的判断

现在的架构是"一套全局状态 + 一堆直接操作全局目录的函数"。版本隔离会把这个问题顶到台面上：
`mods()`、`game_dir()`、`export()`、`import_files()` 都在假设"只有一个游戏目录"。

真正成熟的做法是引入 **Instance（实例）** 这一层显式概念：

```
Instance { id, name, game_version, loader, isolate, java_override, memory_override }
```

所有资源操作都变成"对某个 instance 操作"，UI 上也就自然有了"当前实例"这个上下文
（PCL 的实例设置页、Prism 的实例侧栏都是这个模型）。

这件事和"版本隔离"是同一件事的两面。建议先做隔离，但**按 Instance 的模型去做**，
而不是简单地给 `game_dir()` 加个参数——否则下次做多实例还要再拆一遍。
